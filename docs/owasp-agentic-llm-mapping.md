# OWASP Agentic AI / LLM Top 10 Mapping

Satisfies Req 16.1/16.2 (`.sdd/specs/001-agent-architecture-enhancements/spec.md`).
Maps each risk in the **OWASP Top 10 for LLM Applications (2025)** — the
canonical "LLM Top 10", which folds agentic-autonomy risk into LLM06 Excessive
Agency — to this project's concrete mitigating control, or to an explicit
acceptance/deferral where no dedicated control exists yet. Every row cites the
implementing module and, where one exists, its test file, so a reviewer can
verify the claim against running code rather than prose.

A second table below extends this to the **OWASP Top 10 for Agentic
Applications (2025-12)** — the "Agentic AI Top 10" (ASI01–ASI10) — added per
`docs/cross-repo-adoption-backlog.md` X-13. The two tables are deliberately
non-overlapping: the LLM Top 10 folds agentic-autonomy risk into a single
entry (LLM06 Excessive Agency), while the Agentic AI Top 10 is the risk
taxonomy for a system with goals, tool access, memory, and multi-step
autonomy — a different granularity, not a duplicate one.

This document owns the mapping only; each control is owned and maintained by
its own component (see `plan.md`'s Components section). Update this table
whenever a cited file's mitigating behavior changes materially, not on every
unrelated edit to that file.

## OWASP Top 10 for Agentic Applications (2025-12) Mapping

| # | Risk | Status | Mitigating control | Citation |
|---|------|--------|---------------------|----------|
| ASI01 | Agent Goal Hijack | Partial / accepted | No dedicated hijack-detection exists (a manipulated objective isn't distinguished from a legitimate one). Blast radius is bounded the same way as LLM01: even a hijacked run can't escape the tool allow-list, approval hook, or token budget, and a stopped run persists no session history — only `stop_reason == "completed"` saves — so a hijacked trajectory can't poison a future turn via saved history. | `app/agents/guardrails.py` (`run_guarded`, `_GuardedToolset`); `app/api/v1/agent.py` (`stop_reason == "completed"` gate on `save_history`); `tests/unit/agents/test_guardrails.py` |
| ASI02 | Tool Misuse and Exploitation | Mitigated | Direct correlate of LLM06 below: a native `toolset.filtered` allow-list, an `approval_hook` for dangerous tools, and a pre-side-effect token-budget check gate every tool call. Refused tools stay **visible** in the model's schema (not hidden), so a hallucinated or exploit-attempt call still reaches `call_tool()` and is recorded, not silently dropped. | `app/agents/guardrails.py`; `tests/unit/agents/test_guardrails.py` |
| ASI03 | Identity and Privilege Abuse | Partial / accepted | Session ids are server-issued and HMAC-signed (`{principal.id}.{token}.{signature}`); `authorize_session` 403s on any malformed or cross-principal id via `secrets.compare_digest`. `Principal.id` is a one-way hash of the API key, never stored or logged. The accepted gap: `Settings.api_key` holds exactly one key today, so `POST /v1/rag/ingest` writes into the single process-wide vector store with **no principal binding** — a second API key would make this cross-principal corpus poisoning, and the module docstring flags it as required reading before that change. | `app/security/principal.py` (module docstring, `derive_principal_id`); `app/services/session_service.py` (`authorize_session`); `app/api/v1/rag.py` (`ingest`) |
| ASI04 | Agentic Supply Chain Vulnerabilities | Accepted | No real tool, plugin, or MCP-server surface exists yet to carry this risk — the only registered tool is `mock_web_search`, a stub returning canned data, itself double-guarded (`app_env != "production"` *and* `enable_mock_tools`, with the import deferred so mock code can't run even if misconfigured). `docs/tool-design-conventions.md` plus the `real-tool-conventions-guard` pre-commit hook force a conscious review the moment a real tool is added — revisit this row then, especially for any third-party plugin/MCP dependency. | `app/agents/chat_agent.py` (mock-tool gating); `app/agents/tools_mock.py`; `docs/tool-design-conventions.md`; `.pre-commit-config.yaml` (`real-tool-conventions-guard`) |
| ASI05 | Unexpected Code Execution | Accepted | No code-execution or shell/subprocess tool exists in this codebase at any status — the only tool returns a fixed stub string. Not applicable today; revisit the instant any tool is added that generates or runs code/commands. | `app/agents/tools_mock.py`; `docs/tool-design-conventions.md` ("Status: deferred") |
| ASI06 | Context Management and Retrieval Manipulation | Partial / accepted | Shares LLM04/LLM08/LLM09's control surface, viewed from the agentic angle (does poisoned or stale retrieved context change future agent behavior?). Ingestion requires authentication, limiting who can poison the corpus. The CRAG workflow doesn't trust a single retrieval pass — it widens the search and re-evaluates via a structured `RelevanceVerdict` — and every synthesized claim is grounded to a citation validated against the hits actually retrieved *this run* (`validate_citations`/`order_hits`), so stale or tampered context can't silently pass through as an unverifiable assertion. | `app/api/v1/rag.py` (`ingest`); `app/workflows/corrective_rag.py` (`search`/`evaluate`/`synthesize`); `app/workflows/citation.py`; `app/models/rag.py` (`RelevanceVerdict`) |
| ASI07 | Insecure Inter-Agent Communication | Accepted | Not applicable: this codebase runs exactly one agent (`chat_agent`) plus one code-defined workflow (`corrective_rag`, a fixed search/evaluate/synthesize path — not multiple cooperating agents). There is no agent-to-agent messaging protocol, no A2A/MCP peer, and no sub-agent delegation for this risk to apply to. Revisit if a genuine multi-agent construction is ever adopted. | `CLAUDE.md` ("Multi-agent adoption gate" note, X-16) |
| ASI08 | Cascading Failures | Mitigated | A timed-out LLM call returns a safe fallback **immediately with no retry** (a consistently slow provider isn't a transient failure to pile retries onto), while genuinely transient errors get bounded exponential backoff with jitter. The whole-workflow timeout is a *separate* ceiling from the per-call one, mapped to HTTP 504 independently. On shutdown, each store/client closes independently through `_close_quietly` (logs, doesn't raise) so one failing close can't block the rest; the background `cleanup_loop` swallows and logs any non-cancellation error so a transient store failure can't kill it. | `app/workflows/rag_llm.py` (`_run_agent_with_retry`); `app/api/v1/rag.py` (`asyncio.timeout` → 504); `app/lifespan.py` (`_close_quietly`, `cleanup_loop`) |
| ASI09 | Human-Agent Trust Exploitation | Partial / accepted | Every refused, denied, or budget-blocked tool attempt is recorded to an `AuditTrail` and shipped to the caller as `ChatResponse.audit` — a human reviewing a run sees the mechanical record of what was blocked and why, not only the model's own narrative of what happened. Grounded citations (ASI06 above) mean a synthesized answer's claimed sources are independently checkable against what was actually retrieved, not merely asserted. No dedicated detection exists for a persuasive-but-wrong model explanation talking an operator into approving something — the `approval_hook` itself is a caller-supplied callable, so its trustworthiness is outside this codebase's control. | `app/agents/guardrails.py` (`AuditTrail`); `app/models/agent.py` (`ChatResponse.audit`); `app/workflows/citation.py` |
| ASI10 | Rogue Agents | Mitigated | Every agent run is request-scoped and bounded by `max_iterations` plus a pre-side-effect token budget under a closed `StopReason` vocabulary — there is no standing/persistent agent process that could compromise, misalign, or drift over a long horizon between requests. Session history is TTL-bounded and actively trimmed on every save, so even a compromised session can't accumulate unbounded state across many turns. | `app/agents/guardrails.py` (`StopReason`, `run_guarded`); `app/stores/session_store/_trim.py`; `app/lifespan.py` (`cleanup_loop`, session TTL) |

## Notes on scope

- **"Mitigated"** means a concrete, tested control exists and is wired into
  the production path (not just a dev-only or conditional path).
- **"Partial / accepted"** means a real control reduces the risk's blast
  radius or likelihood but does not eliminate it, and the residual risk is
  knowingly accepted rather than silently unaddressed.
- **"Accepted"** means the risk is judged low today given the current design
  (e.g. no secrets in the system prompt) with no dedicated control — revisit
  if that assumption changes (e.g. the system prompt starts carrying
  sensitive context).
- Requirement 15's tool-design conventions (naming, pagination, lenient
  parsing) are a code-quality/reliability concern for future real tools, not
  a distinct OWASP Top 10 risk, and are tracked separately in
  `docs/tool-design-conventions.md`.
- The Agentic AI Top 10 table's status vocabulary (Mitigated / Partial /
  accepted / Accepted) reuses the same three definitions above — there is no
  separate "not applicable" status. A risk whose preconditions don't exist in
  this codebase today (ASI04, ASI05, ASI07) is recorded as **"Accepted"**:
  the same "revisit if that assumption changes" caveat applies, and each such
  row names the concrete change that would make it apply again.
